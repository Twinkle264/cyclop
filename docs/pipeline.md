# Проверки, сборка и выпуск одной командой

Из корня репозитория, на macOS с Swift 6 и Command Line Tools или Xcode:

```sh
./Scripts/pipeline.sh
```

Это режим `check`: проверка ключей обеих локализаций, совпадения версии сайта
с `Scripts/version`, тесты на сторы, release-сборка приложения, проверка
файлов, версии и подписи бандла, ответ Now Playing helper. Ошибка на любом
шаге останавливает пайплайн с ненулевым кодом. Готовое приложение:
`build/Cyclop.app`. Скрипт работает и при запуске из другой папки.

Приложение автоматически не запускается. Проверка 15-секундного запуска с
файлом на полке остаётся в `.github/workflows/build.yml`: её подготовка меняет
настройки Cyclop, поэтому переносить её на пользовательскую машину нельзя.
Наведение, кнопки, медиа и изменённые функции проверяются вручную по
[release-checklist.md](release-checklist.md).

## Локальный образ

```sh
./Scripts/pipeline.sh dmg
```

Те же проверки плюс `build/Cyclop-<версия>.dmg`. Приложение собирается один раз,
через существующий `dmg.sh`. Подпись по умолчанию ad-hoc. Для Developer ID и
нотаризации используются переменные из [signing.md](signing.md).

## Публикация релиза

1. Поднять `Scripts/version` и `softwareVersion` в `docs/index.html`.
2. Написать непустой `docs/releases/<версия>.md`, включая авторов изменений.
3. Пройти ручной чеклист, закоммитить и отправить изменения в `origin/main`.
4. Дождаться зелёного `build.yml` на выпускаемом коммите. Если CI не стартовал
   из-за изменения только документации, запустить `build.yml` вручную.
5. Настроить пять секретов подписи из [signing.md](signing.md) в своём форке
   и авторизовать GitHub CLI (`gh auth login`).
6. Запустить:

```sh
./Scripts/pipeline.sh release --manual-checked
```

`--manual-checked` означает, что ручной чеклист уже пройден, и разрешает
публикацию. Скрипт требует чистый `main`, совпадающий с `origin/main`, новый
тег, заметки, секреты и успешный CI. GitHub CLI явно направляется в `origin`,
чтобы команды в форке не попали в родительский репозиторий.
Все адреса отправки `origin` также должны указывать на этот репозиторий;
отдельный push URL в другой репозиторий блокирует выпуск.

После локальных проверок существующий `release.sh` отправляет тег. Затем
пайплайн находит запуск `release.yml` именно для этого тега и коммита, ждёт
результата и выводит ссылку на релиз. Образ собирается и публикуется на GitHub.
Скачайте опубликованный образ и проверьте запуск вручную.

Если ошибка произошла после отправки тега, тег автоматически не удаляется.
Откройте Actions своего форка и разберите или перезапустите существующий
прогон. Повторный запуск пайплайна остановится на проверке занятого тега.

## Проверка самого скрипта

```sh
python3 Scripts/test-pipeline.py
```

Тесты работают во временной папке, заменяя сборку и внешние команды. Ничего
не публикуют и не запускают Cyclop. Это проверка управления пайплайном;
реальную сборку проверяет `./Scripts/pipeline.sh`.
